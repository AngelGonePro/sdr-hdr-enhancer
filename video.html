High-Precision Opus / FLAC (experimental, test toggle)
Always applied, not optional (per direct request): Opus/Vorbis encoding always uses 32-bit float internal precision (-sample_fmt flt -ar 48000) feeding the encoder - Opus/Vorbis themselves are lossy codecs with no user-controllable output bit depth, this is purely about avoiding intermediate rounding during decode/filter/downmix before the lossy compression step. FLAC output always standardizes to 24-bit/48kHz (-bits_per_raw_sample 24 -ar 48000) - confirmed via direct research that ffmpeg's own flac encoder caps at 24-bit regardless of input format anyway, so this was already the practical result, just made explicit and consistent across every FLAC output path in this app now instead of only some.
Matrix-encode with Dolby Pro Logic II-compatible spatial encoding at the fold-to-stereo step, then layer the rest of the channels on top via this app's real 7.1 upmix — ONE audio track, not two — ON by default now that it's confirmed to produce ordinary, standard Vorbis with no special tagging. Only relevant to Integrated Engine mode. Uses ffmpeg's own native aresample=matrix_encoding=dplii implementation directly, not hand-derived phase-shift math.

Single-track chain, confirmed via direct end-to-end testing: source → DPLII matrix-encode → this app's validated compressor/limiter/LUFS/limiter safety chain (same values proven against the real Blade Runner 2049 stress test) → stereo FLAC (all of the above baked in here) → this app's own real, already-validated 7.1 upmix (the same one always used) built from that DPLII-processed stereo → ONE 7.1 Vorbis track. Confirmed via a real test run: correctly produces channels=8, channel_layout=7.1 as the file's only audio stream - not a second track, since multiple audio tracks aren't reliably usable in every container this app can output (MP4 in particular).

Codec-agnostic by construction - confirmed via direct code review, not assumed: this works identically for DTS/DTS-HD MA/TrueHD/AC3/E-AC3/PCM sources - track selection only ever reads channel COUNT, never codec name, since the whole chain operates on whatever PCM ffmpeg decodes, regardless of the original bitstream format. Fundamentally different from Dolby Vision/HDR10+ (which need explicit per-format extraction because a decode destroys them) - no per-codec detection needed or built here, since none is needed.

On Atmos specifically, since AC3/E-AC3/TrueHD can carry it: a normal decode (same as the plain fold) never extracts Atmos's object-based (JOC) data regardless of DPLII being on or off - only a pure, untouched -c:a copy preserves Atmos, and Integrated Engine mode is inherently a re-encode. Not a gap DPLII introduces; it processes whatever bed channels come out of the decode uniformly either way, never confusing an Atmos-carrying source for a plain one.

Automatic fallback if DPLII fails on an unusual source: the downmix stage verifies its own real output (not just exit code) and automatically retries with the plain bass-managed fold if DPLII's matrix encoding didn't produce anything usable - no confirmed real case triggers this, but it's a genuine safety net rather than letting the whole job fail.

Real bug found and fixed via direct measurement, not assumed - LFE/bass content: feeding LFE directly into aresample=matrix_encoding=dplii alongside everything else massively under-represents it - confirmed via a real synthetic 5.1 test source with known per-channel frequencies (bandpass+astats measurement): LFE came out ~19dB quieter than the uniform ~7dB gap seen across every other channel, while the plain fold correctly preserved it. This matches a real, independently documented finding from the DPLII community (HandBrake/Dolby Labs testing: "the LFE channel in DPL2's phasing is flawed... was better without the lfe channel phasing") - a known real limitation of DPLII's own matrix math for bass content, not a bug in this implementation specifically. Fixed the same way that community actually fixes it: LFE is now excluded from the matrix encode itself (matrix-encoding only the other 5 or 7 channels as 5.0/7.0) and mixed back into both output channels directly afterward with plain gain, no phase matrix. Confirmed via direct re-test: LFE now comes out within about 1dB of the old plain fold's own LFE level, and every other channel's level is unaffected.

One honest, important limit, confirmed directly rather than assumed - please read this part: the 7.1 upmix does NOT literally decode DPLII's phase-encoded spatial information. Checked ffmpeg's own official bug tracker directly (ticket #10230, still open as an unimplemented feature request): software Pro Logic II decoding does not exist anywhere, including in ffmpeg itself - a real decoder does adaptive, real-time psychoacoustic steering, not a fixed mathematical inverse, which is exactly why it's historically only ever existed in licensed hardware chips, never software. What genuinely does carry through: the upmix operates on the DPLII-processed, safety-chain-protected stereo mix rather than a raw fold, so those quality/loudness choices aren't lost - but the literal phase relationships are not recoverable by this or any software upmix. A real Dolby Pro Logic II hardware decoder fed the underlying stereo mix directly remains the only way to actually recover that, and this single-track output doesn't expose that mix separately.

SDR → HDR10 Expansion
Process for HDR10 output — ON by default. Auto-detects whether the selected video track is already HDR or genuine SDR (via its color transfer characteristic - smpte2084/arib-std-b67 indicate HDR, anything else is treated as SDR - the same detection already shown as the green/yellow "Already HDR"/"SDR" badge next to each track above) and uses a different processing step for each, automatically, no separate toggle to remember. SDR source: the original expansion - gamma/saturation boost, then a BT.709→BT.2020/PQ tonemap - unchanged from before. Already-HDR source (e.g. a genuine 4K UHD Blu-ray rip): that expansion is skipped entirely instead of double-applying it - confirmed via a real report that running it unconditionally on already PQ/BT.2020-encoded pixels (treating already-correct HDR values as if they were BT.709 SDR needing conversion) produced visibly wrong colors on export. The source's real color values are already correct HDR10 in this case, so there's nothing to convert - crop, denoise, sharpen, and framerate handling all still apply completely normally either way, since those are independent of this toggle.

Real mastering metadata now preserved for already-HDR sources (new), not just passed through pixel-wise: confirmed via a real 4K UHD source (genuine MaxCLL 4111 nits, MaxFALL 201 nits, extracted directly from the file's own Mastering Display/Content Light Level side data) that this app was previously REPLACING that real, accurate metadata with its own SDR-oriented Brightness Reference slider value (100-255 nits) on every already-HDR export - badly understating what the content actually is regardless of whether the pixels themselves were correct. A display trusting the old, wrong metadata would have no reason to render this content's real bright highlights at their intended brightness. Fixed by extracting the source's own real mastering-display/MaxCLL/MaxFALL directly (new `get-hdr-metadata` main process call - requires restarting the app after this update, like any main.js change) and using those exact values for the output's metadata instead of inventing new ones - falls back to the Brightness-Reference-driven values only for genuine SDR→HDR grades, where there's no real prior mastering info to preserve since this app is the one creating it.

Why this is the right kind of "enhancement" for already-HDR content, not pixel-level tweaks: a source with real, accurate embedded metadata like this was professionally graded by a colorist - automatically boosting its contrast/saturation further would be working against a deliberate creative choice, the opposite of the SDR case (where this app is filling in a grade that never existed at all). Correcting the metadata so displays render the existing grade the way it was actually mastered is a real, verifiable improvement; guessing at further color changes on top of real graded HDR content isn't one this app makes without evidence it actually helps.
Honest limit: this is real, working color expansion (highlight gamma + saturation boost into a wider BT.2020/PQ container, verified to produce valid HDR10 metadata) — but it is not equivalent to manual grading in DaVinci Resolve's Color page. This is an automated approximation, not a recreation of what DaVinci's Inverse DRT + Color Space Transform node workflow achieves. For the best possible result, that manual workflow is still the better tool — this is the automatable version for when that's not practical.
Corrected a real bug (confirmed via a direct report that SDR→HDR output "looks worse" than the source, then measured directly): the metadata peak used to be a fully independent slider (defaulted to 1000 nits) while Brightness Reference — the setting that actually controls how bright the output pixels get pushed — defaulted to only 150. Measured this directly on real reference SDR white (code 235): it only ever reached about 128 real nits of output brightness, while the file's own metadata was telling every display "this content goes up to 1000 nits." Confirmed the real consequence by rendering an actual frame through a metadata-respecting tonemap (what a real HDR TV does) at the old mismatched values — the result came out badly dark and flat, since the display correctly assumed there was far more real headroom than the pixels actually contained and rolled off accordingly. That's the "looks worse" symptom, not a subjective grading complaint. Fixed structurally, not just by picking better numbers: metadata now always reads directly from Brightness Reference, so there's no longer a way for these two to disagree, whether you set Brightness Reference manually or via "Analyze Source Brightness" below (which had the exact same silent mismatch before this fix, since it only ever calibrated Brightness Reference too).

Brightness Reference is therefore the one real control for both how bright the output actually looks and what the file honestly claims about itself. Default (150) is calibrated safe for worst-case content (pure, fully-saturated colors) with this tool's gamma/saturation settings. Real footage rarely reaches that extreme — "Analyze Source Brightness" samples this specific file's actual peak brightness and empirically finds a calibrated, safe ceiling for it directly (the same test-then-trust method used throughout this tool), which is often meaningfully higher than the generic default — confirmed directly on a real test clip that raising it toward the top of the slider's tested-safe range (220, still without clipping) produces a visibly punchier, less flat result than the old default once metadata is honest again. Worth running on every source rather than trusting the generic default blind.
Process HDR expansion in 4:4:4, output stays whatever the encoder normally uses — ON by default. Researched directly: applying a nonlinear transfer function (exactly what the PQ/HDR conversion above does) to already-subsampled 4:2:0 chroma reconstructs measurably differently than applying it at full chroma resolution first — most noticeable in saturated colors, which this source's own saturation boost specifically pushes toward. Upsamples to 4:4:4 before the gamma/saturation/PQ conversion, downsamples back afterward — final file's chroma subsampling is unchanged either way, so this has no compatibility or hardware dependency, unlike the output toggle below.
Output the final file itself in 4:4:4 (experimental) — OFF by default. The toggle above already captures the real benefit (better precision during the actual PQ/HDR color transform) without this one's risk — this toggle only helps if your source has real 4:2:2/4:4:4 chroma detail to begin with, which no source discussed in building this tool has had, so it's a larger file for identical color information plus real playback risk for no upside in that case. NVIDIA's decode hardware genuinely supports 4:4:4 HEVC decode (confirmed directly from NVIDIA's own Turing announcement), but decode throughput for it isn't unlimited — a resolution-dependent ceiling that sits closer at 4K than 1080p, confirmed this is a real, unresolved risk at 4K specifically even after fixing NVEncC's own --level auto bug (this toggle already applies the fix: explicit level/tier 6.2/High instead of auto-detection). Same generation requirement applies to Intel — see the alert above when Intel is selected. AMD has no 4:4:4 support in any current GPU at all and this toggle is disabled outright when AMD is selected. libx265 (CPU) supports 4:4:4 fully regardless of hardware generation, with no decode-throughput ceiling to worry about since there's no dedicated decode silicon involved.

Real bug found and fixed via direct measurement, not assumed: 4:4:4 carries exactly 2x the raw data volume of 4:2:0 at the same resolution (confirmed directly: full-resolution chroma on both planes vs quarter-resolution — measured 2.000x precisely, matching HEVC's own spec exactly). The bitrate/buffer settings used to be identical regardless of this toggle, forcing the encoder to represent twice the data within the same bit budget — exactly what caused a real report of visibly worse blocking and color reproduction specifically when this toggle was on. Fixed: bitrate target, max-bitrate, and VBV buffer size now all double when this toggle is active, matching the real 2x multiplier HEVC's own spec defines for 4:4:4 profiles (which this app's level/tier choice below already anticipated, but had never actually been applied to the real rate-control values until now).

Chroma priority, NVIDIA only - confirmed via source-level research, not assumed: a separate real report (a subtle near-black warm color tint visible in 4:2:0 output but missing in 4:4:4) traced to `--chroma-qp-offset` defaulting to 0 (chroma gets equal QP priority to luma) - 4:2:0's own chroma subsampling inherently reinforces a weak, spatially-consistent tint through averaging before the encoder ever sees it; 4:4:4 has no such protection. Verified directly in NVEncC's own source code (NVEncCore.cpp) that this flag maps straight to NVIDIA's native NVENC API parameters (cbQPIndexOffset/crQPIndexOffset), and confirmed a live NVEncC session log showing the real default ("QP Offset cb:0 cr:0") - this is genuine, first-party-confirmed behavior, not a guess. Added `--chroma-qp-offset -2` for 4:4:4 output specifically, NVEncC only.

Extended to 4:2:0 too, and confirmed safe for already-HDR passthrough - both specifically researched, not assumed: x264's own documented defaults are -2 for 4:2:0 and -6 for 4:4:4 - meaning chroma priority is a sensible baseline for regular 4:2:0 encoding too, not something unique to 4:4:4. NVEncC's own neutral 0 default doesn't replicate that smarter behavior on its own, so this now applies unconditionally for NVEncC regardless of chroma output mode. On whether this could make already-HDR passthrough worse: a real technical document on HDR/WCG chroma QP determination confirms negative chroma offsets are an established, validated technique specifically for HDR content ("verified that visual quality is better or similar, at same or lower bitrate"). That same source quantifies exactly why the SDR-conversion case benefits most specifically: converting BT.709 into a BT.2020 container (this app's own SDR->HDR pipeline) mathematically reduces the maximum available chroma magnitude before the encoder ever sees it (Cr drops from 0.5 to 0.28, Cb from 0.5 to 0.44) - already-HDR passthrough is natively BT.2020 already and skips that whole transform (confirmed via `buildHdrPixelFilters()`'s own early return for that case), so it doesn't have that specific compounding cause, but the general HDR chroma-QP benefit still applies. Combined with this app's generous VBR ceiling (not tight CBR), the realistic effect is a modestly higher achieved bitrate, not a luma-quality tradeoff - no real mechanism found by which this could make already-HDR conversion worse.

Checked the other GPU vendors specifically, since this fix is NVIDIA-only: extensive research into QSVEncC's (Intel) own documentation and real user command examples found no chroma-specific QP offset equivalent at all - its own `--qp-offset` is confirmed to be a completely different, unrelated parameter (temporal pyramid reference-layer QP, not chroma/luma balance). This app's own code shares the same toolArgs construction between NVEncC and QSVEncC for other settings, so this was a real, catchable risk - sending NVIDIA's flag to QSVEncC could have made the encode fail outright on an unrecognized option, now explicitly scoped to NVEncC only to prevent that. AMD/VCEEncC doesn't support 4:4:4 at all (already covered above), so this question doesn't apply there. Bottom line: Intel 4:4:4 output doesn't currently have an equivalent fix available for this specific chroma-priority issue - the underlying hardware/API may simply not expose this level of control the way NVIDIA's does.

Dynamic HDR Metadata Preservation (experimental)
Preserve Dolby Vision metadata through re-encode — OFF by default, experimental, auto-enables when the selected video track actually carries Dolby Vision RPU data (same detection as the "Already HDR" badge - own status line below confirms it either way). Manually turning this off after it auto-enabled is respected and won't be re-forced back on for the same track; switching to a different track re-evaluates fresh. Only does anything when Process for HDR10 output above is also on. What this is, and why it's different from converting anything: researched this directly first - there is no reliable way to convert Dolby Vision metadata into genuine HDR10+ (the community's own Dolby Vision tooling authors describe this as not a simple reformatting job, and nothing this app could implement would be more solved than that). What IS real and achievable: Dolby Vision is strictly more capable than HDR10+ anyway (true per-frame dynamic metadata, not per-scene), and a source that already has it doesn't need anything converted - only preserved through the re-encode instead of silently dropped, which is what happens today. Extracts the source's real Dolby Vision RPU data (via dovi_tool, a separate download - see setup below) and supplies it directly to the encoder alongside the normal re-encode, so crop/denoise/sharpen/framerate settings all still apply exactly as normal on top.

Honest limits, stated plainly: confirmed via NVEncC's and QSVEncC's own documentation that both support --dolby-vision-rpu <file> --dolby-vision-profile <profile>, and libx265 (via ffmpeg's -x265-params) supports the same two parameters natively - all three are wired in below. VCEEncC (AMD): no confirmed support found researching this - this toggle has no effect there, falls back to the static HDR10 metadata preservation above only. Nobody involved in building this has a Dolby Vision-capable display or validation tooling to confirm the final output actually plays back as real Dolby Vision - this is a real, researched implementation of a genuine, established technique (the same RPU-extract-and-inject pattern real encoding communities use), not a guess, but it's shipped unverified end-to-end the same honest way the untested AMD/Intel RIFE path elsewhere in this app is.

Update (confirmed via real-world report): Jellyfin did not detect Dolby Vision on a real output - exactly the kind of gap the caveat above was written for. Researched this specifically: multiple independent Dolby Vision community reports describe ffmpeg's MKV muxing as unreliable at correctly signaling DV unless the container's frame rate is explicitly forced at the final mux step - one direct account traced a player not detecting DV to exactly this, confirmed by remuxing with the fps explicitly set and having it start working. This app's final mux step had no explicit frame rate declaration at all - fixed, now forces it whenever Dolby Vision preservation is active. Genuinely unclear yet whether this alone fully resolves it (a second real possibility: the separate timing-fix pass this app also runs on the raw encoder output could be affecting the embedded DV data, not confirmed either way) - use the new "Keep intermediate files" debug toggle below to inspect each stage directly (e.g. with dovi_tool info or MediaInfo) if this doesn't fix it, to narrow down exactly where it's actually being lost rather than guessing further blind.

Real root cause found and fixed (confirmed via direct investigation, not the mux-timing theory above): a user report of completely missing metadata (zero side_data on the output, confirmed via direct ffprobe) turned out to be a genuine profile mismatch, not a bug in the mux/timing logic at all. Their actual source is Dolby Vision Profile 7 - the dual-layer format used on UHD Blu-ray rips (confirmed via ffprobe showing dv_profile=7, el_present_flag=1) - but this app was extracting that RPU untouched (still Profile 7) while telling the encoder to inject it as Profile 8.1 (the dropdown's default), a real mismatch that explains the silent, complete metadata loss. Fixed by adding -m 2 to the extract-rpu command - dovi_tool's own documented RPU-conversion mode that converts a Profile 7 RPU to genuine Profile 8.1 compatibility during extraction, the same real technique the whole Dolby Vision community uses for exactly this UHD-Blu-ray-rip scenario (confirmed via dovi_tool's own README and multiple independent community tools built specifically around this conversion step).

One honest caveat on this fix, found during the same research, not smoothed over: Profile 7 comes in two real variants - MEL (Minimal Enhancement Layer) and FEL (Full Enhancement Layer). This conversion strips the Enhancement Layer entirely, which is the correct, lossless-for-RPU-purposes thing to do for MEL content, but the DV community has found that "Complex FEL" sources sometimes use their Enhancement Layer for actual brightness expansion - discarding it in those specific cases can cause incorrect tone mapping, not just a harmless metadata trim. Dedicated community tools built around this exact conversion (dovi_convert, DV7toDV8) specifically detect and skip "Complex FEL" files by default for this reason. This app doesn't currently detect that distinction - if the converted output's HDR looks tonally off after this fix (not just "no DV badge," but genuinely wrong-looking brightness/contrast), that's the specific thing to suspect, and turning this toggle off (falling back to static HDR10 metadata only, which was already correct throughout this investigation) is the safe fallback.
Fully automatic, per direct request - this dropdown is hidden unless it's actually needed. The source's real profile is read directly from its own DOVI configuration record: Profile 7 sources get their RPU automatically converted to genuine Profile 8.1 compatibility (dovi_tool's own documented -m 2 mode - the same real technique the DV community uses for UHD Blu-ray rips specifically); Profile 8 sources get their exact sub-variant read directly from the base layer's own signaled compatibility (8.1 vs 8.4); Profile 5 sources pass through as-is. Nothing here needs to be touched for any of that. The dropdown above only appears (and only then does it actually matter) on the rare case detection can't read a profile at all - the status line above shows exactly which situation you're in.

Mechanism (confirmed via direct research, not guessed): a pre-stage pipes ffmpeg -c:v copy -bsf:v hevc_mp4toannexb -f hevc (the source's original compressed video, byte-for-byte, converted to a raw elementary stream) into dovi_tool extract-rpu, producing a standalone RPU file - the same real workflow used throughout the Dolby Vision encoding community (confirmed via multiple independent guides describing this exact pipe). That RPU file is then supplied to the actual encoder via --dolby-vision-rpu/dolby-vision-rpu=, decoupled from however the encoder receives its actual video (this app's own piped y4m stream, in most cases) - which is what lets Dolby Vision preservation and this app's own filtering (crop/denoise/sharpen) work together instead of being mutually exclusive.

Real muxing fix (confirmed via a user's actual uploaded output file, checked directly, not guessed): the frame-level RPU data was confirmed present and completely correct in the encoder's own output all along - the actual problem was that ffmpeg's own matroska muxer cannot synthesize the container-level "DOVI configuration record" descriptor that many players and tools look for, when muxing a raw stream that only carries per-frame RPU data (confirmed via ffmpeg's own source and multiple independent real-world reports of this exact limitation - not fixable with any ffmpeg flag, including -strict unofficial, which was tried and directly confirmed not to help). The real, community-standard fix - genuinely used throughout the Dolby Vision encoding community for exactly this - is mkvmerge (part of the free MKVToolNix package), used specifically for the final mux step whenever Dolby Vision preservation is active. ffmpeg is still used for every other stage; only this one final step is swapped.

Minimal smoothing (hqdn3d) — OFF by default. Framerate Conform (movies only — no AI, no interpolation)
Conform to a whole-number frame rate instead of interpolating — OFF by default. A genuinely different technique from all 5 options above: zero synthesized frames, so the rubberbanding/warping problems documented above and throughout this app's development are structurally impossible here — there's no motion estimation happening at all to get wrong. This is the same technique DaVinci Resolve's Clip Attributes frame rate change and Premiere's Interpret Footage use — confirmed via a direct quote from Blackmagic's own forum: "a frame for frame conversion to a different rate with no interpolation or weird cadence... changes the playback speed". This is a genuine, if small, change to the movie's real playback duration — the source runs very slightly longer in real time than a whole-number-fps target, so conforming to the higher whole number makes it play very slightly shorter. Audio is automatically time-corrected to match (asetrate/aresample, the same validated technique from the audio converter tool's Framerate Sync Correction) — no separate audio pass needed, unlike the manual cross-tool step required for the 5 interpolation options above. Mutually exclusive with all 5 interpolation options above — selecting this turns those off and greys them out, and vice versa, since they solve the same "mismatched frame rate" problem in fundamentally incompatible ways: one adds real new content (frames), this one only ever relabels timing on frames that already exist. Only sensible for near-whole-number conforms like 23.976→24 - there's no "48fps"/"60fps" option here, since conforming (not interpolating) to a much higher target would speed the movie up dramatically rather than smooth its motion, which is a completely different effect (fast-forward, not smoother playback).

Two different mechanisms depending on encoder choice, per direct request: with an external-tool encoder selected (NVEncC/QSVEncC/VCEEncC), this uses an input-side -r override right at the actual decode point - those paths already decode the source exactly once, so this reaches the identical result in that same single pass. With a built-in ffmpeg encoder instead (external tools off), this uses a genuine lossless stream-copy pre-stage (-c:v copy, no decode/re-encode at all for this step) via the setts bitstream filter.

Corrected mistake (confirmed via a real user report of quality loss): the first version of the stream-copy path used setts=ts=N/fps/TB, which independently reassigns both PTS and DTS to the same formula - ffmpeg's own documentation explicitly warns this is unsafe when B-frames are involved (this source has them), and it's what broke decode ordering and caused the reported corruption. Fixed by scaling the source's own ORIGINAL PTS and DTS by the same constant ratio instead (setts=pts=PTS*sourceFps/targetFps:dts=DTS*sourceFps/targetFps) - since B-frame reordering is just a fixed offset between a frame's DTS and PTS, uniformly scaling both preserves that offset (and therefore correct decode order) instead of erasing it, while still landing on the exact same evenly-spaced target-fps timing.

Works alongside everything else in this app (confirmed, not assumed): HDR expansion, cropping, denoise/sharpen, and encoder choice all apply exactly as normal. Chapter timestamps are automatically rescaled to match the new duration when Passthrough Chapters is on. The AC3 audio-delay auto-detection, Audio Delay/Offset, and Duration Correction features all still work too and compose correctly with this toggle's own audio stretch - Duration Correction's own target duration accounts for the conform automatically so the two corrections agree instead of fighting each other.

Enable external encoder tools (NVEncC/QSVEncC/VCEEncC) — ON by default. These are separate downloads, not part of ffmpeg. Only useful if you actually have the matching hardware (NVIDIA/Intel/AMD) and have downloaded the tool for it — see the note below for where; turn this off if you don't.
⚠ AMD GPUs do not support 4:4:4 HEVC — confirmed as a genuine hardware limitation (a direct statement from AMD's own community forum: "no AMD GPU supports 4:4:4 encoding... lack of physical support"), not just a missing driver feature. AMD's video engine (VCN) handles encode and decode through the same unified hardware block, unlike NVIDIA's separate encode/decode chips — no evidence found of a decode-only exception. Both 4:4:4 toggles further up have been disabled while this encoder is selected.
⚠ Intel needs 10th Gen Ice Lake or newer for 4:4:4 HEVC — both encode and decode arrived together at that generation, confirmed directly from Intel's own Quick Sync history, so there's no separate encode-vs-decode gap the way NVIDIA has. Unlike the AMD alert, the 4:4:4 toggles further up are not disabled here, since Intel genuinely supports this — just confirm your specific hardware is 10th Gen or newer before relying on it, older iGPUs will fail outright.
Default lowered from 18 to 15 after a real report of visible softness on a heavily-grained film — researched this directly: NVENC hardware encoding has no real equivalent to x265's grain-preserving psycho-visual tuning (confirmed by multiple user reports on NVEnc's own GitHub describing this exact complaint), and adaptive quantization actually reallocates bits away from detailed/textured regions toward flat ones, so it isn't a fix here either. More bits via a lower CRF is the one lever that reliably helps across every encoder — this will produce noticeably larger files in exchange for that.
GPU-accelerated decode during the actual encode (separate from the detection-sampling toggles above) — moves video decoding onto the GPU to reduce CPU load, which may be the actual bottleneck if your GPU sits well under 100% during encodes. The color/HDR filtering itself stays on CPU either way, unchanged and unaffected. Confirmed by direct testing: NVIDIA off is stable, on correlated with a real system crash (bugcheck 0xA, IRQL_NOT_LESS_OR_EQUAL) during NVEncC encoding — likely from running concurrent CUDA decode and NVENC encode on the same GPU while a driver-level bug exists. That's the opposite situation from the detection toggles above (which don't run concurrently with an active encode at all), so all three default off here regardless of vendor. Only one can be active at a time. Worth retrying NVIDIA after a driver update if you want the CPU headroom back.
NVIDIA (CUDA) — OFF by default. Confirmed crash correlation, see above.
Intel (QSV) — OFF by default. No confirmed crash history with this path, but also not directly tested here — worth verifying stability on your specific hardware before relying on it.
AMD (via D3D11VA — the same real decode path used for AMD detection above) — OFF by default, same reasoning as Intel.

GPU color/HDR processing via libplacebo (experimental) — OFF by default. Replaces the validated eq/zscale color pipeline with libplacebo's inverse_tonemapping, which is genuinely faster and scene-adaptive. Direct testing traced the corruption seen previously to the inverse-tonemapping path specifically — not the rest of the pipeline, and not the choice of curve (bt2446a and the library default produced identical corrupted output; disabling only inverse mode restored correct colors). Switched to the "spline" curve, the one a real user report found actually usable for inverse mode after finding bt2446a "insanely crushed" there specifically. Testing here is limited to a software Vulkan renderer that Mesa's own maintainers label "not a conformant Vulkan implementation, testing use only" — genuinely unclear whether the remaining corruption is specific to that non-conformant renderer or a real libplacebo limitation on actual hardware. Worth testing directly on your GPU and comparing against the default pipeline before trusting it for real output.

For NVIDIA GPUs. Download: github.com/rigaya/NVEnc/releases — get the latest release, download the zip for Windows x64. The exe inside is named NVEncC64.exe (confirmed directly — this exact filename shows up consistently across the tool's own docs and real user reports). Extract it anywhere and either put that path here, or add its folder to your system PATH and leave the field as just NVEncC64.exe.
For Intel GPUs — this is what actually runs on Intel integrated graphics (iGPU) on most systems, not a separate thing from QSV. Download: github.com/rigaya/QSVEnc/releases — Windows x64 zip. Expected exe name: QSVEncC64.exe (same author, same consistent naming convention as NVEncC — not independently confirmed the way NVEncC64.exe was, so double-check the exact name inside the zip you download in case a release changes it).
For AMD GPUs. Download: github.com/rigaya/VCEEnc/releases — Windows x64 zip. Expected exe name: VCEEncC64.exe (same naming convention as the other two — verify against what's actually inside the zip you get, same caveat as QSVEncC).
NVENC HDR10 metadata is incomplete when run through ffmpeg directly — confirmed: this build's hevc_nvenc rejects the mastering-display/max-cll flags outright, and it's not build-specific — ffmpeg's NVENC wrapper reads this data from frame side-data that nothing in a plain SDR→HDR pipeline provides, not from CLI flags. Still gets correct color space signaling (primaries/transfer/matrix), just not the detailed metadata. For complete HDR10 metadata at GPU speed, enable external encoders above and use NVEncC instead — genuine, working native support. libx265 also has complete metadata, just CPU-speed.
hevc_qsv's HDR10 support looks genuinely more complete than NVENC's — unlike NVENC, Intel's own engineers added -qsv_params support for master-display/max-cll directly (a real, merged ffmpeg patch), and a real, confirmed example shows actual working HDR10 metadata in real output. This tool sends that flag automatically when HDR is on. I can't verify it works on your exact build from here — if it fails, the full error panel will show why, and QSVEncC (external tool, enable above) is the fallback with guaranteed-complete metadata.
hevc_amf's HDR10 metadata uses -mastering_display/-content_light — documented directly on AMD's own GitHub wiki with a complete working example. I could not verify this against your exact build — my own test environment's ffmpeg doesn't have AMF support compiled in, so I can't confirm these flags are recognized the way the NVENC ones turned out not to be. If it fails, the full error panel will show why, and VCEEncC (external tool, enable above) is the fallback with guaranteed-complete metadata.
Duration Correction
Correct audio to match the video's real duration — OFF by default. Different problem than Framerate Sync above: some source audio streams decode to measurably less (or more) actual content than the video's true runtime, a property of how the source was originally encoded — confirmed via direct sample-count testing on a genuine AC3 file in the audio converter tool this was ported from. This tool already knows the video's real duration automatically, so unlike that standalone tool, there's no manual ffprobe/paste step — just compares the selected track's own decoded length against it.
Select an audio track above to auto-detect its actual decoded duration.
Audio Delay / Offset
Shift the audio track by a fixed amount — OFF by default. For source files where audio consistently arrives early/late by roughly the same amount throughout (the AC3 offset issue diagnosed in the audio converter tool applies here too, if this video's audio track has the same source characteristics).
Positive value = delay audio (pad start with silence) — use when audio arrives too early. Negative value = trim from the start — use when audio arrives too late.
Applying this requires re-encoding audio (a filter can't run on a stream-copied track) — switches from passthrough to a lossless intermediate automatically when this is on, then re-encodes back to the source track's own original codec for the final output, so it still looks like passthrough rather than an obviously different, larger file.

Setup: download MKVToolNix from mkvtoolnix.download (the free installer includes both mkvmerge.exe and mkvextract.exe), install it, and set the path above to wherever it installed mkvmerge.exe (commonly C:\Program Files\MKVToolNix\mkvmerge.exe) - mkvextract is auto-derived from this same path (same folder, filename swapped), no separate field needed.
Used unconditionally by several features now, not just Dolby Vision: the final mux step whenever Dolby Vision/HDR10+ preservation is active, PGS subtitle OCR (mkvextract pulls each subtitle track for conversion), and the Native NVEncC/QSVEncC 4:4:4 paths' own mux stage. Moved here from a DV-only section it used to be hidden inside, per direct request that every external tool dependency have a discoverable UI field regardless of which feature happens to need it first.
Integrated Engine mode always outputs Vorbis audio, and MP4/MOV have no real, standard tag for it — confirmed directly: ffmpeg mux this as generic mp4a (normally meaning AAC), which many players strictly expect to actually be AAC and may fail to play correctly, even though ffmpeg itself handles it fine. MKV supports Vorbis natively with no such issue — switching back is the safer choice unless you have a specific reason MP4/MOV is required here.
